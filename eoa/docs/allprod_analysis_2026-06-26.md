# LFmall 전상품(ALL_PRODUCT_INFO) 분석 리포트 (2026-06-26)

## 개요
LFmall 판매중 전상품 DB(`ALL_PRODUCT_INFO.json`, 11.6GB)를 스트리밍 슬림화하여
경량 카탈로그(`allprod_slim.jsonl`, 314MB)로 변환하고 전수 프로파일을 집계함.
원본은 `PROD_STS_CD='90'`(판매중) 필터된 STB_PRODUCT × STB_ITEM 조인 결과.

## 목적
- 11.6GB 대용량 DB가 현 환경에서 분석 가능한지 검증
- 전 카탈로그의 브랜드·가격·품목·할인 분포 파악 → 기획전 기획의 모수 기준선 확보

## 기존 환경 분석 (처리 가능성)
- **전체 로드 불가**: 11.6GB를 메모리(3.8GB)에 적재 불가, 샌드박스 디스크(9.3GB)로 복사도 불가.
- **스트리밍 가능**: 평문 JSON(`{"<SQL>":[{...}]}`)을 라인 파서로 처리, 약 26MB/s.
- **제약 대응**: 45초/호출 한도 + 백그라운드 미유지 → byte-offset 재개형 청크(약 14회)로 전수 처리 완료.
- 결과: 무손실 전수 슬림 성공.

## 전수 프로파일 (2,512,069건)
- **상품수**: 2,512,069건 (PROD_CD 중복 0 — 전건 고유)
- **브랜드**: 고유 18,851개 (브랜드코드 결측 216건)
- **상품유형(PROD_TYPE)**: 10(일반) 2,511,644 / 50 423 / 20 2 — 사실상 전부 일반상품
- **가격(PROD_PRICE)**
  - 평균 681,268원 · 중앙값 239,000원 (평균≫중앙값: 고가 상품에 의한 우편향)
  - P10 ~ P90: 약 1.7백만원선까지, P99 6,013,510원, 최대 254,980,000원(이상치성 초고가)
  - 가격대 분포: 30~100만 654,441 / 100만+ 489,428 / 10~30만 439,607 / 1~3만 416,979 / 5~10만 212,885 / ~1만 152,474 / 3~5만 146,255
- **할인(DC_RATE)**: 할인적용(>0) 상품 비중 **33.0%** (전수 기준)
  - ※ 파일 앞부분 샘플에서는 65%로 나왔으나, 파일이 브랜드순 정렬이라 편향된 수치였음. 전수 33%가 정확.
- **품목군(ITEMKIND 상위 2자리) 상위**: L3 406,869 / E0 288,685 / 2C 223,699 / P0 181,409 / 7H 125,898 / T0 102,233 / D0 90,932 / J0 78,526

## 개선 방향 (활용)
1. **기획전 모수 기준선**: 기획전 편성 시 전 카탈로그 가격대·품목 분포 대비 해당 기획전의 편중도를 정량 비교 가능.
2. **온톨로지 확장 후보**: 가격포지셔닝(가격대 밴드), 할인강도(DC 구간)를 기획전 속성 축으로 파생 가능.
3. **슬림 자산 재사용**: 314MB 경량 JSONL로 향후 분석은 초 단위로 가능(전수 집계 12초).

## 개선 시 기대효과
- 11.6GB 원본 재파싱 없이 반복 분석 가능 → 분석 리드타임 7분 → 12초.
- 기획전 상품 구성을 전사 카탈로그 기준으로 상대 평가 → 기획 의사결정 근거 강화.

## Appendix
- 슬림 필드: PROD_CD, BRAND_CD, ITEMKIND_CD, PROD_PRICE, DC_RATE, PROD_TYPE
- 산출물: `outputs/allprod_slim.jsonl`(314MB), `outputs/allprod_summary.json`(원수치)
- 처리 방식: 재개형 청크 스크립트(`outputs/chunk_slim.py`), 상태파일(`allprod_state.json`)
- 주의: 가격 최대값(2.5억) 등 이상치성 데이터는 별도 검수 권장. 브랜드코드는 STB_BRAND와 조인해 명칭 매핑 가능.

# 파생 속성 축 추가 (온톨로지 정식 연결)

전상품 가격 데이터를 기획전 상품 매핑과 결합해 **기획전당 2개 파생 축**을 신설하고 파이프라인에 정식 반영함(7축 → 9축).

## 축1. 가격 포지셔닝 (pricetier)
기획전 소속 상품의 **중앙 판매가** 기준 4구간.

| 구간 | 기준(중앙가) | 기획전 수 |
|---|---|---|
| 가성비형 | ~5만 미만 | 36 |
| 실속형 | 5~15만 | 160 |
| 프리미엄형 | 15~40만 | 132 |
| 럭셔리형 | 40만+ | 11 |

## 축2. 할인 강도 (discount)
기획전 전 상품의 **평균 할인율**(미할인 0% 포함) 기준 4구간.

| 구간 | 기준(평균할인) | 기획전 수 |
|---|---|---|
| 저할인 | ~15% 미만 | 101 |
| 중할인 | 15~30% | 156 |
| 고할인 | 30~50% | 56 |
| 초고할인 | 50%+ | 26 |

## 반영 범위
- `build_data.py`: AXIS_KEYS·CONFIG.AXES·AXIS_WEIGHT에 pricetier/discount 추가, 기획전 조립 시 자동 산출.
- `daily_run.py`: AXES 9축으로 갱신 → diff/스냅샷/MD에 자동 포함.
- 검증: EVENTS=339, 9축 정상, 분포 위 표와 일치.

## 활용
'가격포지셔닝 × 할인강도' 교차로 기획전 성격을 분류 가능(예: 럭셔리형×저할인=정가 럭셔리, 가성비형×초고할인=초특가 떨이). 조건 조합 빌더에서 신규 필터로 즉시 사용.

# 파생 속성 축 추가 ② — 쿠폰 출처/유무 (coupon)

페이지 검증(진행중 106건 전수)에서 드러난 '퍼블리싱 쿠폰 ≠ DB 쿠폰' 구조를 온톨로지 축으로 정식화. `LST_PLAN_COUPON`(DB)과 `TB_LFM12_EXHB_CARD_LIST`(페이지 카드 퍼블리싱)를 결합해 4값으로 분류(9축 → 10축).

## 축. 쿠폰 출처/유무 (coupon)

| 값 | 정의 | 기획전 수 |
|---|---|---|
| DB쿠폰 | LST_PLAN_COUPON에 등록 | 28 |
| 퍼블리싱쿠폰 | 페이지 카드 FCFS_CPN·PLUS혜택·멤버혜택(확정성 높음) | 58 |
| 퍼블리싱혜택카드 | 구매혜택(B_BENEFIT)만 — 쿠폰일 수도, 혜택 안내일 수도 | 75 |
| 쿠폰없음 | 위 어디에도 해당 없음 | 178 |

## 설계 근거
- DB쿠폰과 페이지 퍼블리싱 쿠폰은 **겹침 0** — 완전히 분리된 두 시스템.
- 페이지 실측 결과 B_BENEFIT 카드는 실제 다운로드 쿠폰이 아닌 경우가 있어, 확정 쿠폰(FCFS/PLUS/멤버)과 분리해 '퍼블리싱혜택카드'로 별도 분류.
- 진행중 106건 검증: 86건 쿠폰 확인, 20건 신호미검출(대부분 '퍼블리싱혜택카드' 그룹) → 이 축으로 우선검토 대상(퍼블리싱혜택카드 75건)을 바로 필터 가능.

## 반영 범위 / 검증
- build_data.py: AXIS_KEYS·CONFIG.AXES·AXIS_WEIGHT(coupon:1.1) 추가.
- daily_run.py: AXES 10축 → diff/스냅샷/MD 자동 포함.
- 검증: EVENTS=339, coupon 4값 분포 위 표와 일치.

## 활용
- 'DB엔 없지만 페이지엔 쿠폰' = 퍼블리싱쿠폰/퍼블리싱혜택카드 → 쿠폰 운영 데이터 정합성 점검 대상.
- '쿠폰 출처 × 가격포지셔닝 × 할인강도' 교차로 프로모션 설계 정밀화.
