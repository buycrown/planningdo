- **AI PLAN(기능3·4·5)**: 매 클릭 Gemini 호출, **추천/참신 2분할**, 속성·연결구조 출력. 소스 B 속성을 실제 분석에 활용 확인. (`js/ai_plan.js`)

## 1. 개요

현재 `event_ontology_analysis`는 **가공된 `data.json`(117개 EVENTS, 5축 속성)** 위에서 동작하는 바닐라 JS 모듈형 SPA입니다. 이번 업그레이드의 핵심은 세 가지입니다.

1. **실제 LFmall DB(16개 테이블)** 를 적재해, `data.json`을 **하이브리드 벡터화 산출물**로 교체한다.
2. 매일 오전 10시 **Cowork 예약 작업**이 DB를 재분석하고, `Gemini PRO API`로 **검색 조건의 '속성' 세트를 자동 증감(추가/삭제)** 한다.
3. 툴에 **신규 기능 6종**(2-소스 조건 빌더 · 온톨로지 맵 · 추천/참신 2분할 AI PLAN · 매 호출 Gemini · 속성 명시형 결과 · NL·브랜드 추천 Gemini 연동)을 **index.html이 아닌 별도 파일**로 추가한다.

이 모든 과정을 **1 Orchestrator + 3 전문 에이전트(분석·개발·검증)** 가 관리합니다.

**현재 → 목표 상태 비교**

| 구분 | 현재(v3.1) | 목표(v4) |
|---|---|---|
| 데이터 출처 | 수작업 가공 `data.json` (117건) | 실제 DB 16테이블 자동 적재 (LST_PLAN 337건 기준) |
| 속성(facet) | 고정 5축 키워드 | 하이브리드 벡터 + AI 비전 추출 속성, 매일 자동 증감 |
| 유사도 | 키워드 가중 자카드 | 키워드 자카드 + 임베딩 코사인(하이브리드) |
| 온톨로지 | 유사도 점수만 | 트리플(주어·관계·목적어) 그래프 + 시각 맵('커넥텀' 스타일) |
| AI PLAN | 단일 추천 | **추천 기획전 + 참신한 기획전** 2분할 |
| 운영 | 수동 | 매일 10시 자동 갱신 + 설명서(MD) 자동 생성 |

## 2. 목적

- **데이터 정합성**: 추정/가상 데이터를 실제 운영 DB 기반으로 대체해 분석 신뢰도 확보.
- **살아있는 온톨로지**: 속성이 고정되지 않고, 매일 데이터·실제 기획전 페이지 변화에 따라 자동 진화.
- **'보이지 않던 속성'의 발굴**: DB 컬럼만으로는 잡히지 않는 기획전의 실제 표현(톤·비주얼·카피·구성)을 AI가 직접 페이지를 보고 속성화 → **DB에 없는 차별적 인사이트** 확보(본 프로젝트 최우선 가치).
- **실행 가능한 기획 산출**: 서술형이 아니라 **속성과 속성 간 연결구조**로 "어떤 기획전을 만들지"를 제시.

### 3.2 현재 데이터 모델

- `CONFIG`: `AXES`(theme·benefit·product·visual·brand), `AXIS_WEIGHT`, `SYN`(동의어), `models`(`gemini-3.5-flash`/`gemini-3.5-pro`), `gemini_api_key`.
- `EVENTS[*].kw`: 축별 키워드 배열. `similarity()`는 이 `kw`로 가중 자카드를 계산.
- 한계: ① 키워드가 수작업 가공이라 확장성↓ ② 매출/유입이 가상값 ③ 속성이 고정 ④ 페이지 실제 표현(비주얼·카피)은 미반영.

### 3.3 실제 DB 핵심 매핑 (적재 시 기준 키)

- **마스터**: `LST_PLAN`(337건) — `PLAN_SQ`(기획전 키), `PLAN_NM`, 기간, `PLAN_TYPE/PLAN_TYPE_CD`, `CATE_TYPE`, `BENEFIT_TYPE`, 쿠폰 필드(`CPN_DISCOUNT_PER/WON`), `ATTR_C1~5`·`ATTR_N1~3`(확장 속성), `OPEN_YN/VALID_YN`(노출 여부).
- **성과**: `PLAN_REVENUE`(334건) — 기획전 PV/UV, 상품 PV/UV, 거래액/매출액, 결제수량, 쿠폰·총 할인비용율, 주문건수, 상품UV CR, 객단가. → **가상 매출값을 실제값으로 대체.**
- **속성/코드**: `TB_LFM12_PLAN_ATRT`(코드 단위 속성) + `COMMON_CODE`(코드→라벨 해석) + `TABLE_PROPERTIES`(596개 컬럼 정의, 적재 자동화의 스키마 사전).
- **구성요소**: `LST_PLAN_PROD`/`PLAN_PROD_INFO`(상품), `STB_BRAND`(브랜드), `STB_COUPON`/`LST_PLAN_COUPON`(쿠폰), `LST_PLAN_CATEGORY`/`LST_PLAN_CTGY_PBSH`(카테고리), `PLAN_DISPLAY_POSITION`(전시 위치), `LST_PLAN_SITE`(노출 사이트), `LST_PLAN_TYPE`/`LST_PLAN_DTL`.
- **페이지 URL 규칙**: `https://m.lfmall.co.kr/app/event/{PLAN_SQ}` → AI 비전 검수 진입점.

## 4. 타사 분석 (온톨로지 구현 벤치마크)

참고 기사(디지털데일리, 2025-10-14) 기준 두 선도 사례에서 v4 설계 원칙을 도출합니다.

- **팔란티어(Palantir) — Kinetic Element / Action Type**: 단순 지식 연결을 넘어 "특정 조건에서 어떤 **행동**을 취할지"를 온톨로지에 부여. → v4 적용: 속성·관계에 더해 **"이 속성 조합이면 이런 기획전을 만들라"는 Action(추천/참신 PLAN)** 을 온톨로지에 결합.
- **솔트룩스 '구버/커넥텀' — Triple 기반 지식그래프**: 정보를 **주어+관계+목적어** 트리플로 표현하고, 마인드맵과 달리 **엄격한 관계 기준**으로 노드-링크를 시각화. → v4 적용: **온톨로지 맵**을 트리플 그래프로 구현(아래 5.5).
  - 노드 타입: `기획전`, `속성`(테마/혜택/상품/비주얼/브랜드), `브랜드`, `카테고리`, `성과버킷`.
  - 엣지(관계): `has_attribute`, `targets_category`, `offers_benefit`, `features_brand`, `similar_to`(유사도 임계 이상), `performs_as`(성과 버킷).
  - 마인드맵과의 차별점(기사 핵심): 무한 연상 확장이 아니라 **관계·속성·인과에 합리적 기준**을 부여 → v4는 유사도/지지도(support)/신뢰도(confidence) 임계값으로 엣지를 필터링.

## 5. 개선 방향 (핵심 설계)

### 5.1 데이터 파이프라인 & 하이브리드 벡터화

**파이프라인 (Python, 매일 10시 실행)**

```
[1] 적재    16개 JSON/JSONL 로드 → TABLE_PROPERTIES로 스키마 검증
[2] 정규화  COMMON_CODE/TB_LFM12_PLAN_ATRT로 코드→라벨 해석
[3] 조인    PLAN_SQ 기준 마스터+성과+상품+브랜드+쿠폰+카테고리 통합 → plan_doc[]
[4] 속성화  규칙기반 facet 추출(테마/혜택/상품/비주얼/브랜드) + 성과 버킷
[5] 벡터화  ── 하이브리드 ──
            (a) 로컬: facet 키워드 TF-IDF → 희소 벡터 (오프라인, 비용 0)
            (b) 의미: 각 plan_doc 요약문을 Gemini 임베딩 API로 dense 벡터화
            (c) 결합: sim = α·자카드(로컬) + β·코사인(임베딩)  (기본 α=0.5, β=0.5)
[6] 산출    data.json(EVENTS/CONFIG) + vectors.json(임베딩 캐시) 생성
```

- **하이브리드 선택 이유(승인됨)**: 로컬 벡터로 1차 구조·속도·비용을 잡고, 임베딩으로 의미적 유사도를 보강. 임베딩은 **변경분만 재계산**(plan_doc 해시 캐시)해 비용 최소화.
- 산출된 **속성(facet) 전체 집합 = 툴 조건 빌더의 '속성' 등록 소스**.

### 5.2 온톨로지 엔진 (트리플 모델)

- `ontology_engine.js`를 확장해 `buildTriples(events)` 추가: 각 기획전을 (주어=PLAN, 관계, 목적어=속성/브랜드/카테고리) 트리플 집합으로 변환.
- 임베딩 코사인 유사도를 `similarity()`에 하이브리드로 합산(엔진 파일 분리: `vector_engine.js`).
- **연관규칙 마이닝**(속성 동시출현 support/confidence/lift) → '참신한 기획전' 후보(높은 lift지만 미사용 조합) 산출 근거.

### 5.3 멀티 에이전트 아키텍처 (1 Orchestrator + 3 전문 에이전트)

요청하신 5단계 사고 흐름을 **각 에이전트의 공통 작업 프로토콜**로 내장합니다.

```
                      ┌──────────────────────────┐
                      │  ORCHESTRATOR (조율자)     │
                      │  - 작업 분해/우선순위      │
                      │  - 에이전트 간 산출물 전달 │
                      │  - 게이트/승인 관리        │
                      └─────────┬────────────────┘
            ┌───────────────────┼───────────────────┐
   ┌────────▼────────┐ ┌────────▼────────┐ ┌────────▼────────┐
   │ 분석 에이전트     │ │ 개발 에이전트     │ │ 검증 에이전트     │
   │ DB 적재·벡터화·   │ │ 파이프라인/UI    │ │ 테스트·오류 자동 │
   │ 온톨로지·AI 비전  │ │ 기능 코드 작성   │ │ 수정·스타일 점검 │
   │ 페이지 검수       │ │ (파일 분리)      │ │ (서브에이전트)   │
   └─────────────────┘ └─────────────────┘ └─────────────────┘
```

**공통 5단계 사고 프로토콜**
1. **프로젝트 시작**: 구조 분석 → 코드베이스 탐색 → 프레임워크/라이브러리 파악 → 코딩 스타일·패턴 학습(`.clinerules` 준수: UTF-8 BOM, Cohere 디자인 토큰, 브라우저 검증 정책).
2. **작업 계획**: 컴포넌트 식별 → 구현 순서 결정 → 종속성 파악.
3. **실행**: 파일 생성/수정 → 코드 작성 → 패키지 설치 → 테스트 코드 작성·실행.
4. **검증·개선**: 테스트 → 오류 자동 수정 → 스타일·패턴 재학습.
5. **완료**: 산출물·설명서(MD) 생성, Orchestrator 보고.

> 구현 형태: Cowork **서브에이전트(Agent 도구)** 로 분석/개발/검증을 분리 호출하고, Orchestrator는 본 세션이 담당. 에이전트 정의(역할·입출력·게이트)는 `/agents/*.md`로 문서화.

### 5.4 매일 오전 10시 Cowork 예약 작업

- `mcp__scheduled-tasks`로 매일 10:00 실행 잡 등록(cron `0 10 * * *`).
- 잡 내용: ① 파이프라인 재실행 → ② Gemini PRO로 **속성 세트 diff(추가/삭제)** 산출 → ③ 온톨로지 맵 재생성 → ④ **변경 설명서 MD**(`/docs/ontology_update_YYYY-MM-DD.md`) 자동 작성: 무엇이 추가/삭제됐는지, 근거(데이터·페이지 변화), 맵 갱신 요약.
- 어제 대비 속성 증감은 `attributes_history/`에 스냅샷으로 보관해 추적.

### 7.2 검증 필요 항목 (⚠️ 진행 전 확인 권장)
1. **모델 명칭**: `CONFIG.models`의 `gemini-3.5-pro`/`gemini-3.5-flash`는 Google 공개 모델군(`gemini-2.5-pro`, `gemini-3-pro` 등)과 명칭이 다릅니다. 사내 프록시/별칭인지, 실제 호출 시 404 여부 확인 필요.
2. **API 키 형식**: 현재 키가 `AQ.Ab8RN...`(OAuth형 토큰 추정)으로 표준 `AIza...` API 키와 다릅니다. 만료/스코프 이슈 가능 → 유효성 1회 검증 필요.
3. **전체 즉시 검수 비용**: 노출 중 기획전 약 수백 건 페이지 검수는 시간·토큰 소모가 큽니다. (대안: 우선순위/효율 상위부터 배치 진행). 진행하되 배치 크기 합의 필요.
4. **페이지 렌더링**: `m.lfmall.co.kr`는 JS 렌더링일 가능성 → WebFetch 대신 **Claude in Chrome**으로 검수(확장 연결 필요).
5. **`.clinerules` 충돌**: 기존 룰에 "브라우저 검증 금지"가 있으나, 본 프로젝트 핵심은 **브라우저 기반 페이지 검수**입니다. 이 룰을 본 작업에 한해 예외 처리할지 확인 필요.
