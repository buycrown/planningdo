[LFmall 어필리에이트 - 인플루언서 신청 화면]  v2.2
인플루언서가 가입 신청(= 회원가입)을 작성하는 화면입니다.

- index.html : 신청 화면 (이 파일을 브라우저로 열면 됩니다)
- site-config.js : 공용 경로 모듈 (window.LFSite)  ★ 2026-08 신규
               로컬/배포 환경을 자동 판별해 화면 간 이동 URL 을 계산합니다.
               04_로그인, 03_활동내역, 02_ADMIN 의 site-config.js 와 '동일한 내용'의 사본입니다.
               한 곳을 고치면 나머지 3곳에도 똑같이 복사해 주세요.
               HTML 의 이동 링크는 <a data-lf-link="login"> 으로만 적습니다. (href 금지)
- auth.js    : 공용 인증 모듈 (window.LFAuth)
               비밀번호 정책 검증 / PBKDF2 키 스트레칭 / 보안 컨텍스트 점검 담당.
               04_로그인, 03_활동내역, 02_ADMIN 의 auth.js 와 '동일한 내용'의 사본입니다.
               한 곳을 고치면 나머지 3곳에도 똑같이 복사해 주세요.
- app.js     : 화면 동작 로직 (이메일 중복확인, SNS 다중입력, 파일첨부, 비밀번호 검증,
               약관검증, 전송)
               아래 4개 주석 마커로 구간이 나뉘어 있습니다. 테스트 하네스가 이 구간을
               잘라 Node 에서 실행하므로 마커를 지우거나 이름을 바꾸지 마세요.
                 @pure:sns-start ~ end          SNS 전송 배열 순수 로직
                 @dom:sns-start ~ end           SNS 행 추가/삭제/↑ DOM 로직
                 @pure:emailcheck-start ~ end   이메일 중복확인 상태머신 (DOM 비의존)
                 @dom:emailcheck-start ~ end    중복확인 버튼/메시지 DOM 연결
- lfmall-logo.png : 상단 로고 이미지

[v2.0 변경 사항]
1. 'LFmall 아이디' 입력 항목과 회원가입/아이디찾기 버튼을 삭제했습니다.
   (서버 시트의 'LFmall ID' 컬럼은 기존 데이터 보존용으로만 남아 있습니다)
2. '비밀번호 / 비밀번호 확인' 항목을 추가했습니다. (v2.2 에서 이메일 바로 아래로 이동)
   - 표시/숨김 토글(눈 아이콘), 강도 인디케이터(약함/보통/강함), 실시간 정책 검증
   - 정책 : 8~20자 / 영문·숫자·특수문자 중 2종 이상 / 같은 문자 3연속 금지 /
            연속 문자열(abcd, 1234) 금지 / 이메일 아이디·휴대폰 뒷자리 포함 금지
   - 이 비밀번호로 '04_로그인' 화면에서 로그인합니다.
3. 신청 전송 시 평문 비밀번호를 보내지 않습니다.
   브라우저에서 PBKDF2-SHA256(120,000회)로 해싱한 pwCsalt / pwClientHash 만 전송합니다.
4. 이미 신청된 이메일·휴대폰번호이면(서버 code:'DUPLICATE')
   '로그인 화면으로 이동' 안내가 표시됩니다.
5. 신청 완료 화면에 '로그인하러 가기' 버튼이 추가되었습니다.

[v2.1 변경 사항 — SNS 대표 채널]
1. 서버 시트가 SNS 를 유형별 컬럼(21 대표채널 / 22 Instagram / 23 YouTube /
   24 X(Twitter) / 25 TikTok / 26 기타)으로 분리 저장합니다.
   ※ 화면이 보내는 요청 형식은 그대로입니다. (snsChannels: [{channel, url}])
      서버가 알아서 유형별로 분류하며, 같은 유형을 여러 개 보내면 줄바꿈으로 병기 저장합니다.
2. 다만 '배열 순서가 대표 채널을 결정' 합니다. snsChannels[0] 의 유형이 21열 대표채널이 됩니다.
   → 화면의 행 순서(위 -> 아래)가 그대로 전송 순서가 되도록 보장합니다.
     (collectSnsChannels() = readSnsRows() -> buildSnsChannels() · 중간 정렬/역순 없음)
3. SNS 입력 영역에 아래 UI 가 추가되었습니다.
   - 안내 문구 : "첫 번째로 입력한 채널이 대표 채널로 사용됩니다."
   - 맨 위 행에 '대표' 뱃지 (행을 추가·삭제·이동해도 항상 맨 위 행을 따라갑니다)
   - 각 행의 ↑ 버튼 : 순서를 한 칸 올려 대표 채널을 바꿉니다. (맨 위 행의 ↑ 는 비활성)
     한 행의 마크업은 [대표 뱃지 줄] + [.sns-row__ctrl = 채널 ▾ / 주소 / ↑ / −] 구조입니다.
4. 기존 기능(도메인 자동 기입, 행 추가·삭제, 최소 1행 유지, 유효성 검증)은 그대로입니다.

[v2.2 변경 사항 — 회원 기본키(PK)가 이메일이 되었습니다]
1. 이메일 = 회원 기본키(로그인 아이디)  (SPEC §1-7)
   서버는 이메일을 trim + 소문자로 정규화해 저장합니다.
   대소문자·앞뒤 공백만 다른 이메일은 '같은 계정' 입니다. (A@x.com = a@x.com)
2. 이메일 입력란 우측에 [중복 확인] 버튼이 생겼습니다. **눌러서 통과해야 신청할 수 있습니다.**
   - 확인 중 : 버튼 비활성 + 스피너 + '확인 중…'
   - 사용 가능 : 초록 ✓ + 이메일 입력란을 readonly 로 잠그고 옆에 [변경] 버튼 노출
                [변경] 을 누르면 잠금이 풀리고 다시 '미확인' 상태가 됩니다.
   - 이미 가입됨 : 빨강 안내 + '로그인 화면으로 이동' 링크 (../04_로그인/login.html)
   - 형식 오류 : '이메일 형식을 확인해 주세요.' (서버를 호출하지 않고 화면에서 걸러냄)
   - 통신 오류 : '확인에 실패했습니다. 다시 시도해 주세요.' → 그대로 다시 누르면 됩니다.
   - 이메일 값이 조금이라도 바뀌면(자동완성 포함) 즉시 '미확인' 으로 돌아가고
     신청하기 버튼이 비활성화됩니다. 확인 중에 값을 바꾸면 늦게 도착한 옛 응답은 버립니다.
3. 필드 순서를 바꿨습니다.
   이메일 → 비밀번호 → 비밀번호 확인 → 이름 → 활동명 → 관심 카테고리 → 휴대폰번호 → 사업자 유무
   (로그인에 쓰는 아이디·비밀번호를 맨 위에 모았습니다)
   ※ 휴대폰번호가 비밀번호보다 아래로 내려갔지만, 휴대폰 입력이 바뀌면 비밀번호를
     다시 검증합니다. ('휴대폰 뒷 4자리 포함 금지' 규칙 유지)
4. 신청하기 버튼 활성 조건 (5가지 전부 충족해야 활성)
   ① 약관 전체 동의  ② 비밀번호 정책 통과 + 확인 일치  ③ 이메일 중복확인 통과
   ④ 보안 컨텍스트(HTTPS)  ⑤ 서버가 구버전 배포가 아님
   미확인 상태로 제출을 시도하면 '이메일 중복 확인을 먼저 해주세요.' 안내와 함께
   이메일 필드로 스크롤·포커스합니다.
5. 서버 오류 코드 분기를 추가했습니다. (SPEC §3-0)
   EMAIL_REQUIRED / INVALID_EMAIL → 이메일 필드로 되돌림 + 중복확인 상태 초기화
   DUPLICATE → 기존대로 '로그인 화면으로 이동' 안내 (동시 가입 대비. 잠금도 함께 해제)

[배포 시 주의 — API_LEVEL 은 3 입니다 (v2.2에서 2 -> 3)]
이 화면은 emailCheck 액션에 '실제로 의존' 합니다.
(이메일 중복확인 통과가 신청하기 버튼 활성 5조건 중 하나)
emailCheck 가 없는 서버에서는 신청이 아예 성립하지 않으므로,
SPEC §3-0-c 의 승격 조건에 따라 API_LEVEL / EXPECTED_API_LEVEL 을 3 으로 올렸습니다.

  · 서버   apps-script.gs        var API_LEVEL = 3;
  · 클라   auth.js 4개 사본       var EXPECTED_API_LEVEL = 3;

★ 배포 순서를 반드시 지키세요 — 서버 먼저, 화면 나중.
  ① apps-script.gs(API_LEVEL=3) 저장 -> initServer() 실행 -> 새 버전 배포
  ② 그 다음에 정적 파일(auth.js 4개 사본 포함)을 호스팅에 올린다
  순서를 뒤집으면 아직 API_LEVEL=2 인 서버가 '구버전' 으로 판정되어
  신청/로그인/활동내역/ADMIN 4개 화면의 입력이 전부 막힙니다.

만약 구버전 서버를 만나더라도 조용히 잘못되지는 않습니다.
화면 진입 즉시 '구버전 배포' 배너가 뜨고 신청 버튼이 비활성화됩니다.
(하네스 email-check.js 의 (7)/(7)-b 케이스가 이 동작을 실행으로 검증합니다)

[검증]
  cd ../공용_서버_문서/_테스트하네스
  node sns-order.js
    · 전송 배열 순서 = 화면 순서 (배열[0] = 대표 채널)
    · 같은 유형 다건 유지 / 미입력·도메인만 입력된 행 제외
    · 행 추가·삭제·↑ 이동 시 대표 뱃지와 ↑ 비활성 상태 추적 (미니 DOM 으로 실제 실행)

  node email-check.js
    · 이메일 중복확인 상태머신 (미확인 → 확인중 → 사용가능/중복/오류 → 값 변경 시 미확인)
    · 신청하기 버튼 활성 조건 32조합 전수 테스트
    · index.html 중복 id 0건 / JS 참조 id 전수 대조 / 필드 DOM 순서
    · 초기화 순서(TDZ) 정적 분석 + 실물 실행 (node --check 로는 잡히지 않는 결함)
    · 기존 기능 회귀 (SNS·비밀번호 강도·약관 전체동의·모달·첨부 안내)

[중요 · 실행 환경]
비밀번호 해싱에 사용하는 WebCrypto 는 보안 컨텍스트에서만 동작합니다.
index.html 을 파일 탐색기에서 더블클릭(file://)하면 신청이 진행되지 않으며
화면 상단에 경고 배너가 표시되고 '신청하기' 버튼이 비활성화됩니다.

  · 로컬 확인 : 이 폴더에서 python -m http.server 8000 실행 후
                브라우저에서 http://localhost:8000 접속
  · 실제 운영 : HTTPS 정적 호스팅에 배포
